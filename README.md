# Сервис поиска мест по интересам

Учебный проект развивает объектную модель (ПР3) в веб-приложение для практических занятий №5–7. Пользователь может искать места по названию, категории и рейтингу. Администратор входит в защищённую область, создаёт и отменяет рекомендации.

## Реализация ПР5–6

- Backend: Flask и REST API поверх существующих моделей, сервисов и JSON-хранилища.
- Frontend: адаптивный интерфейс на HTML, CSS и JavaScript; фильтры обращаются к API через `fetch`.
- Правила предметной области: рекомендация проверяет интерес пользователя, доступность места и отсутствие активного дубля.
- Защита: пароль администратора хранится в окружении как хеш Werkzeug; сессия подписана секретным ключом, cookie имеет флаги `HttpOnly` и `SameSite`; изменяющие API-запросы требуют CSRF-токен. Для API ограничен размер тела запроса; добавлены CSP и защитные HTTP-заголовки.
- Производительность: каталог кэшируется в памяти на 30 секунд (значение настраивается), ответы каталога имеют `Cache-Control`, JSON при записи заменяется атомарно.

## API

Все ответы API используют JSON. Ошибка возвращает объект `{"error": "..."}`.

| Метод и путь | Доступ | Назначение |
| --- | --- | --- |
| `GET /api/health` | открытый | Проверка работоспособности |
| `GET /api/categories` | открытый | Список категорий |
| `GET /api/places?q=&category_id=&min_rating=` | открытый | Поиск доступных мест; фильтры необязательны |
| `GET /api/auth/csrf` | открытый | CSRF-токен и состояние сессии |
| `POST /api/auth/login` | открытый | Вход: `{"username":"...","password":"..."}` |
| `POST /api/auth/logout` | администратор + CSRF | Завершение сессии |
| `GET /api/users` | администратор | Пользователи для формы рекомендаций |
| `GET /api/recommendations` | администратор | Список рекомендаций |
| `POST /api/recommendations` | администратор + CSRF | Создание: `{"user_id":1,"place_id":1}` |
| `POST /api/recommendations/{id}/cancel` | администратор + CSRF | Отмена рекомендации |

Для запросов с изменением данных браузер автоматически передаёт `X-CSRF-Token`, полученный после загрузки приложения или входа.

## Локальный запуск

Требуется Python 3.10+.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python app.py
```

Откройте `http://127.0.0.1:5000`. Для входа задайте `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH` и случайный `APP_SECRET_KEY`. Хеш можно создать в активном окружении:

```bash
python -c "from werkzeug.security import generate_password_hash; print(generate_password_hash(input('Пароль: ')))"
```

Передача `ADMIN_PASSWORD_HASH` предпочтительна; `ADMIN_PASSWORD` поддерживается для локальной разработки. Без заданных учётных данных вход выключен.

Данные хранятся в `data/`. Путь можно переопределить через `DATA_DIR`.

## Развёртывание (ПР7)

Подготовлена контейнерная конфигурация Docker Compose: непривилегированный пользователь, read-only корневая файловая система, отдельный постоянный том для JSON, health check, автоматический перезапуск и журналирование Gunicorn в stdout/stderr.

1. Установите Docker Engine с Compose plugin на Linux-сервере. Создайте `.env` рядом с `compose.yaml`, используя `.env.example` как основу. Сгенерируйте `APP_SECRET_KEY` командой `python -c "import secrets; print(secrets.token_urlsafe(48))"`, задайте имя администратора и хеш пароля из команды выше.
2. Запустите `docker compose up -d --build`. Проверяйте состояние `docker compose ps`, логи — `docker compose logs -f web`, health endpoint — `curl http://127.0.0.1:8000/api/health`.
3. Настройте reverse proxy с TLS-сертификатом и проксированием на `127.0.0.1:8000` по примеру `deploy/nginx-site.conf.example`. Порт контейнера привязан только к loopback. Разрешите во внешнем firewall только SSH и HTTPS (80 нужен для выпуска/обновления сертификата и перенаправления на HTTPS). Для TLS установите `COOKIE_SECURE=true` (Compose уже задаёт его).
4. Обновляйте образ командой `docker compose up -d --build`; храните `.env` вне Git. Резервируйте том `place-data` и периодически проверяйте восстановление копии. Для наблюдения используйте Docker health status и журналы; для production добавьте внешний мониторинг доступности и оповещения.

Фактический внешний сервер в этом репозитории не задан, поэтому здесь подготовлены приложение и воспроизводимый сценарий деплоя; запуск в облаке требует выбранного хостинга и его учётных данных.
